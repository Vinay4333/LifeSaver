# M5 verification: signed partner approval

Date: 2026-10-12. Emulator `emulator-5554` only. The phone was not touched during these tests.

This replaces the first M5 design (emailed secret token), which failed on real ntfy.sh: anonymous email is refused with HTTP 400. See [UNLOCK.md](../UNLOCK.md) for the design.

Relay for the emulator runs: a local stand-in for ntfy on this PC, reached at `http://10.0.2.2:8787` (`-PntfyBase=...`, debug build only, with CORS headers like the real ntfy.sh sends). **Real ntfy.sh and the hosted GitHub Pages page were not exercised.**

## Unit tests (JVM)

`:policy` has 45 tests, all passing. Highlights:

- ECDSA P-256 verification of signatures produced by **the approve page's own code** (`docs/approve/crypto.js`, run under Node's WebCrypto): unlock and partner-change vectors, and the fingerprint format.
- 300 random signatures survive the raw-to-DER conversion; malformed and off-curve public keys are rejected (found and fixed: Java alone accepts off-curve points).
- Engine: pairing needs the candidate's signature; a different key cannot pair or approve; wrong request id, wrong purpose, garbage and an old signature are ignored; cancel, 24 h expiry, reboot and clock-backwards handling; changing partner needs the current partner's signature over the new key (tampering with the key breaks it); after a change only the new key unlocks.
- No private key and no secret in the phone's unlock store.
- The real HTTP client against a local server, including a full pair-and-unlock flow.

## Emulator results

| Step | Result |
| --- | --- |
| Pair with a key made by the page code (Node): paste key, start pairing | App shows the same fingerprint as the partner (`7607-60BF-7079-4415`). Stored state has no private key. |
| Partner signs the pairing request | Within about 8 s the partner is saved. |
| Unlock request: a different key signs it | Ignored. Still locked. |
| Unlock request: real partner signs the wrong request id, and garbage is posted | Ignored. Still locked. |
| Real partner signs the real request | "Unlocked, 14:53 left". A blocked name resolves. |
| Lock now | Blocked again. |
| Change partner to a key created in the app, signed by the old partner (message includes the new key) | Partner changed. |
| Old partner key signs a new unlock request | Ignored. |
| New (in-app) partner approves via the `lifesaver://` deep link and the in-app Approve screen | Unlocked. |
| Open the real approve page (`docs/approve`, served locally, Chrome on the emulator): create key | Page shows public key and fingerprint. |
| Change partner to the page's key, approved in-app | Partner changed. |
| Page request for a **different** key | Warning "This request is for a different key ... Do not approve." Approve button disabled. |
| Page request for this key, press Approve | "Approved. You can close this page." Phone unlocked within seconds and a blocked name resolved. |

## Not verified

- Real ntfy.sh as the relay (publish worked from this PC earlier; poll, CORS from the real page and rate limits were not run).
- The page hosted on GitHub Pages (it needs `docs/approve/index.html` and `crypto.js` published).
- A real second person and device.
- Share sheet and email-draft hand-off (intents not driven on the emulator).
- Window ending after 15 minutes, and a reboot closing the window, with the new engine (covered by unit tests; the earlier reboot test was on the first design with the same timer code).
- `BOOT_COUNT` on the Galaxy A15.
- The content guard staying quiet during a window (code path only).

## Gaps this does not close (until M8/M9)

- After a reboot the VPN is down until someone taps "Turn on protection". No always-on VPN yet.
- The system VPN settings can still disconnect LifeSaver's VPN, and Clear data wipes the stored partner key.
- Pairing is free the first time and software cannot tell who made the key.
- Key loss means lockout (no fallback).
